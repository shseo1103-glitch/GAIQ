## 0. 요약 (Executive Summary)

첨부하신 HTML 코드는 **로그인 → 공정설정/데이터입력 → 결과진단** 3화면 구조의 UI 데모이며, 본인이 명시하신 대로 "완벽하지 않고 UI/UX도 최적화되지 않은" 참고용 목업입니다. 실제 클릭 로직은 슬라이더 값에 대한 **간단한 if-else 룰 기반 판정**(라만 D/G ≤0.13, 커버리지 ≥90%, 전도도 ≥7% 등 3개 중 몇 개 통과했는지)이며, 데이터 저장/사용자 관리/이력추적 기능은 전무합니다.

반면 노트북LM 소스(특허문헌·제품개발계획서)를 조회한 결과, 실제 목표 플랫폼은 다음을 요구하는 것으로 확인됩니다:

- **멀티테넌트 구조**: 연구단체(서울대·단국대 등) / 제조기업(그래핀일렉트릭·그래핀스퀘어 등) / 시험인증기관(KTL·KTR 등) / 플랫폼관리자, 4종 조직이 하나의 생태계에서 데이터를 격리하며 협업
- **1단계(PoC) vs 2단계(사업화 R&D) 이원화된 품질 기준치** — 단순 고정값이 아니라 시간에 따라 상향되는 목표
- **롤투롤(R2R) 연속공정 + 배치(Batch) CVD** 양쪽을 모두 지원하는 공정 파라미터 체계
- **레시피 버전관리, LOT 이력추적(genealogy), 디지털 시험성적서(CoA)+블록체인 해시, 보안/인터록 로그** 등 5개 이력관리 도메인
- **AI 추론 모델 4종**(비전 결함판정 / CVD 가상 시뮬레이터 / 물성 예측·역설계 / 특허·논문 시맨틱 검색) — 현재 데모의 룰 기반과는 차원이 다른 범위

즉, **"첨부 코드 완성"이 아니라 사실상 신규 플랫폼 설계**에 가깝습니다. 아래는 이 격차를 메우기 위한 단계별 작업지시서입니다.

## 1. 프로젝트 목표 및 원칙

1. 그래핀 CVD 합성 공정 데이터와 품질측정 데이터를 축적하고, 규칙기반(1차)/AI기반(2차) 진단으로 공정 개선안을 제시하는 SaaS형 플랫폼 구축

## 3. DB 설계 방향 (ERD 개요)

### 3.1 핵심 엔티티 그룹

**A. 조직/사용자 (Tenant & RBAC)**
- `organization` (org_id, org_type[RESEARCH/PRODUCER/BUYER/CERTIFIER/ADMIN], org_name, geofencing_coords, ...)
- `user_account` (user_id, org_id FK, role[R&D_LEAD/RESEARCHER/PROCESS_ENGINEER/OPERATOR/AUDITOR/PLATFORM_ADMIN], biometric_flag, ...)
- `role_permission` (역할별 화면/기능 접근권한 매트릭스 — CSMS의 `admin_role_permission` 패턴 재사용)

**B. 마스터 데이터 (Metadata)**
- `equipment_model` (T-CVD, PECVD, LPCVD, APCVD, R2R 연속합성설비, 에어젯밀 등)
- `raw_material` (CH4/H2/Ar 가스 순도+LOT, 벤젠/피리딘 등 액상전구체)
- `substrate` (구리 단선/연선 A·B·C-Type 규격, SiO2/Si 웨이퍼, Ge/Si 웨이퍼, PET, 유리, 석영)
- `measurement_equipment` (라만분광기, SEM, AFM, EBSD, 4-Probe저항계, IR카메라, Bulge테스터 등)
- `qc_threshold_spec` (물성항목별 1단계/2단계 합격기준치 — 아래 3.3 표 그대로 마스터화)

**C. 공정 실행 데이터 (Synthesis Batch)**
- `synthesis_batch` (batch_id, org_id, equipment_id, substrate_id, 공정유형[BATCH/R2R], 시작·종료시각)
- `synthesis_process_param` (batch_id FK, 파라미터명, 값, 단위, 타임스탬프) — 시계열 구조, 향후 파티셔닝 고려
  - 챔버온도(℃, 150~2000), CH4유량(sccm, 0.15~200), H2유량(sccm, 0.4~100), Ar유량(sccm, 10~1000), 챔버압력(Pa/mbar), 어닐링시간(min, 10~240), 성장시간(min, 5~120), 롤장력(kg/m, 0.1~5), 권취속도(m/h, 2~10)

**D. 품질측정 데이터 (QC Measurement)**
- `qc_measurement` (batch_id FK, 측정항목, 측정값, 단위, 측정장비, 측정일시, 판정결과[PASS/FAIL])
  - 라만 ID/IG(ratio, ≤0.13/0.10), 라만 I2D/IG, 그래핀커버리지(%, ≥90/95), 전기전도도향상율(%, ≥7/10), 도체도전율(%IACS, ≥102/103), 구리연선굵기(SQ, ≤10/45), 전류인가표면온도(℃, ≤40), 구리사용저감율(%), 케이블무게절감율(%), 구리산화도변화율(%), 비저항변화율(%), 복합도선구리함량(wt%), 복합도선분산균일도(%), 내전압(kV), EUV투과율(%, 펠리클용), 펠리클Yield Strength(GPa), 펠리클수소라디칼내성(hour)
- `raman_spectrum_raw` (batch_id FK, 파장(cm-1) 배열, 강도 배열 — 원본 CSV 저장 또는 JSON)

**E. AI 분석/시뮬레이션 (2단계 확장)**
- `ai_recipe_recommendation` (batch_id FK, 추천파라미터 JSON, 근거설명, 적용여부)
- `ml_calibration_log` (simulation_id, prediction_data JSON, actual_test_data JSON, residual_error, retraining_flag)

**F. 이력/버전관리 (Audit & Traceability)** — CSMS의 `action_log`+Envers 패턴을 확장
- `recipe_version_history` (recipe_id, version_no, change_log, applied_line_id, approver_id, 수정일시)
- `lot_genealogy` (lot_no, raw_material_lot, batch_id FK, defect_coordinates JSON, pass_or_fail)
- `certificate_coa` (certificate_id, batch_id FK, issue_date, pdf_file_hash, blockchain_sha256_hash, approver_id) — **블록체인 연동은 2단계 이후 검토(§7 결정사항 참고)**
- `security_interlock_log` (event_id, trigger_timestamp, sensor_value, action_status, org_id)
- `action_log` (기존 CSMS 패턴 그대로: 모든 CRUD 변경 이력, before/after JSON)

### 3.2 참고: 노트북 원문의 목표 물성 판정기준 요약표 (마스터 데이터 시드값)

| 측정항목 | 단위 | 1단계(PoC) | 2단계(사업화) |
|---|---|---|---|
| 라만 결함도(ID/IG) | ratio | 0.13 이하 | 0.10 이하 |
| 그래핀 커버리지 | % | 90 이상 | 95 이상 |
| 전기전도도 향상율 | % | 7 이상 | 10 이상 |
| 도체 도전율 | %IACS | 102 이상 | 103 이상 |
| 구리 연선 굵기 | SQ | 10 이하 | 45 이하 |
| 전류인가 표면온도 | ℃ | - | 40 이하 |
| 구리 사용 저감율 | % | 5 이상 | 10 이상 |
| 케이블 무게 절감율 | % | 2 이상 | 5 이상 |
| EUV 투과율(펠리클) | % | 85 이상 | 90 이상 |

> 첨부 데모의 임계치(D/G≤0.13, 커버리지≥90%, 전도도≥7%)는 **1단계 기준과 일치**함을 확인했습니다. 즉 데모는 "1단계 PoC용 단순 룰 엔진"이며, 실제 플랫폼은 2단계 기준까지 이원화 관리해야 합니다.

## 5. 개발 프로세스 (기존 CSMS/AI_CMS 방법론 재사용)

1. **1단계 — 요구사항 확정 및 화면명세**: 본 지시서 §7의 결정사항 확정 → 화면명세서(`03-screen-spec.md` 형식) 작성
2. **2단계 — ERD 및 API 계약(OpenAPI) 설계**: §3 ERD 정식화, `docs/api-contract/*.yaml` 작성
3. **3단계 — 백엔드 구현**: Spring Boot, Flyway 마이그레이션, `action_log` 감사로그 전 도메인 적용
4. **4단계 — 프론트엔드 구현**: 화면명세 기반 Vue3 컴포넌트 개발(첨부 데모 UI 톤 참고)
5. **5단계 — 통합검증**: 브라우저 스모크테스트, 버그수정
6. **6단계 — 배포**: pm2 등록, 포트 할당(8000-8999 대역 중 미사용 포트), Caddy 라우팅(필요시)

각 단계 완료 시 `./gradlew compileJava` → `build -x test` → 커밋/푸시 → 완료 이메일 발송(기존 USER.md 규칙 준수)까지 동일하게 적용합니다.

## 6. 단계적 확장 로드맵 (권장)

| 단계 | 범위 | 예상 난이도 |
|---|---|---|
| **1단계 (MVP)** | 단일조직, 룰기반 판정(첨부 데모 로직 확장), 배치/측정 데이터 DB화, 기본 이력조회 | CSMS 수준 — 기존 경험으로 충분히 커버 가능 |
| **2단계** | 멀티테넌트 RBAC(연구/기업/인증기관 3종), 레시피버전관리, LOT추적 | AI_CMS의 권한관리 경험 재사용 가능하나 3-tenant 격리 설계 추가 필요 |
| **3단계** | AI 시뮬레이터(CVD 가상공정 예측), Active Learning 오차보정 루프 | **신규 영역** — 실제 학습데이터 축적 후 별도 ML 파이프라인 필요, 상당한 추가 리소스 예상 |
| **4단계** | 블록체인 CoA 해시, 지오펜싱 보안, 특허/논문 시맨틱검색 | **신규 영역** — 우선순위 낮음, 실질 수요 재확인 필요 |

**권장**: 1단계부터 시작해 실제 사용 피드백을 받으며 2단계로 확장. 3~4단계는 실제 데이터 축적과 비즈니스 필요성이 확인된 후 착수 권장.

## 7. 사용자 결정 필요 사항 (★ 반드시 확인 후 착수)

1. **실제 축적 데이터 존재 여부**: 첨부 데모 헤더에 "그래핀일렉트릭 5~6년 축적 데이터 기반"이라는 문구가 있습니다. **이 과거 실측 데이터가 실제로 엑셀/CSV 등으로 존재합니까?** 존재한다면 초기 시드 데이터로 임포트할 수 있고, 없다면 신규 입력부터 시작하는 시스템으로 설계됩니다.
2. **개발 범위(스코프) 확정**: 위 §6 로드맵 중 **1단계(MVP)만 우선 개발**할지, 아니면 **2단계(멀티테넌트)까지 한 번에** 개발할지 결정 필요합니다. 범위에 따라 DB 설계·인증구조가 크게 달라집니다.
3. **AI 진단 로직의 실제 수준**: 1단계는 첨부 데모처럼 **룰 기반(if-else 임계치 비교)**으로 충분한지, 아니면 처음부터 실제 **머신러닝 모델**(공정파라미터→물성예측)을 학습시켜야 하는지. 후자라면 학습용 데이터셋 규모/출처를 별도로 확인해야 합니다.
4. **사용 조직 범위**: 실제 서비스 대상이 **그래핀일렉트릭 단독 사내 시스템**인지, 아니면 노트북 내용대로 **서울대/단국대 등 연구기관 + KTL/KTR 등 인증기관까지 포함하는 컨소시엄형 플랫폼**인지. 후자면 조직 간 데이터 격리·보안 요구수준이 높아집니다.
5. **시험성적서(CoA) 블록체인 해시**: 특허문헌에 언급된 요구사항이나, 실제 필수 기능인지 아니면 향후 검토 대상인지 확인 필요합니다(구현 난이도·인프라 비용에 영향).
6. **배포 계획**: 기존 프로젝트들처럼 이 VM(20.194.5.165)에 pm2로 배포할지, 별도 인프라(그래핀일렉트릭 사내 서버 등)를 사용할지.
7. **플랫폼 명칭**: 노트북 원문에는 "Graphene AI-QSim"이라는 명칭이 언급됩니다. 이 이름을 그대로 사용할지, 첨부 데모의 "GrapheneElectric AI QC"를 사용할지, 별도 명칭이 있는지.
8. **일정**: 목표 완료 시점(예: WRC 출장처럼 특정 이벤트 데드라인이 있는지)이 있으면 알려주시면 단계별 일정을 역산하겠습니다.
