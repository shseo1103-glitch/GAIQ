## 5. ML 모델 학습 가능성에 대한 현실적 평가

**실측 row 42건(그중 공정+물성 매칭 완전한 것은 10건 미만)**으로는:

- ❌ **딥러닝(신경망) 모델**: 전혀 부적합. 최소 수백~수천 row가 필요하며, 현재 데이터로는 과적합이 필연적.
- ⚠️ **회귀모델(선형/다항/Ridge)**: 부스바 온도상승 데이터(12개 조건, row20-28)처럼 단일 변수(전류)에 대한 반응 곡선은 회귀로 피팅 가능. 단 일반화(다른 SQ, 다른 재질에 대한 외삽)는 위험.
- ✅ **트리기반 모델(Random Forest, Gradient Boosting)**: 소량 데이터에서도 비교적 안정적이나, 42건은 여전히 부족. 최소 100건 이상 확보 전까지는 "모델"이라기보다 **경험적 lookup table + 전문가 보정** 수준으로 사용하는 것이 현실적.
- ✅ **현재 최선의 접근**: (1) 이미지 재판독(그래프 픽셀값 추출)으로 A그룹 내 숫자 미기재 항목 보강, (2) C그룹 외부논문 데이터를 물리모델(예: ρ∝La⁻¹, K∝La^(1/3))의 파라미터 추정에 활용, (3) 실측 데이터가 쌓일수록 회귀→트리기반으로 순차 고도화하는 **단계적 로드맵**.
- **추가 데이터 확보 우선순위**: (a) 2024-7-30 보고서의 IR카메라/전압-온도 원본 이미지 재판독, (b) 위탁개발 완료보고서의 "별첨" 기술문서 확보, (c) 사업계획서 3종의 출처/시기 정리(중복 프로젝트 여부 확인)

## 4. 연선굵기(SQ) 정의

### 4.1 확정 정의 (사용자 확인, 2026-09-07)

> **연선굵기(SQ) = 단선(single wire)을 여러가닥 꼬은 연선(stranded wire)의 (전체) 단면적**
>
> 예: "10 SQ"는 여러 단선을 꼬아 만든 연선의 **총 단면적**이 10mm²라는 의미.
> 통상 **1 SQ = 1 mm²**로 사용됨.

### 4.2 기존 데이터의 SQ값 재해석 주석

| 소스 | 기존 SQ 수치 | 이 정의 기준 재해석 |
|---|---|---|
| `211115_그래핀부스바 검증시험 결과서` (row20-28) | 80SQ, 20SQ | 부스바 자체가 다수 단선의 연선이 아닌 단일 압출 도체(busbar)일 가능성이 높음 — 이 경우 SQ는 "연선의 총단면적" 정의를 busbar 단면적에 유추 적용한 관행적 표기로 해석. 실제 연선(strand) 형태인지 최종 확인 필요 |
| `2025년 창업중심대학 최종보고서` (row35-36) | 약 7SQ (0.08mm×약1,990가닥) | **정의와 정합**: 0.08mm 단선 지름 기준 단면적 = π×(0.04mm)² ≈ 0.00503mm². ×1,990가닥 ≈ **10.0mm²** — SSOT 문서의 "약 7SQ" 표기와는 다소 차이(계산상 약 10SQ에 근접). 실제 압축율(연선은 원형단선을 꼬면서 공극이 생겨 총단면적이 계산값보다 작아짐)을 고려하면 7SQ도 합리적 범위 |
| `[제일테크노스] 연구개발계획서` | 25→40SQ(1단계), →60SQ(2단계) | 정의 적용시 목표 연선의 총단면적이 25~60mm² 범위로, 창업중심대학의 실제품(7SQ, 약10mm²)보다 크게 설계된 대용량(1MW급) 계획으로 일관성 있게 해석됨 (기존 "불일치" 판정was 정의 혼선에서 발생했을 가능성; 정의 확정 후에는 오히려 **스케일이 다른 별개 프로젝트**라는 기존 결론이 강화됨) |
| `그래핀전선과제개요` | SQ 수치 미기재 | 재해석 대상 없음 |

### 4.3 정의 확정에 따른 영향

- 기존 3절(B그룹 교차검증)의 "SQ 불일치" 판정은 **정의 자체의 모호함이 아니라 프로젝트 규모(7kW vs 1MW)의 차이**에서 기인한 것으로 재확인됨.
- 향후 ML 학습 데이터에서 SQ를 공정 파라미터로 사용할 때는 **"연선의 총단면적(mm²)"** 단일 정의로 표준화하여 입력하며, busbar 단면적과 혼용하지 않도록 `substrate_type`(연선 vs 부스바) 필드를 별도로 태깅할 것을 권장.

## 5. ML 방법론 최종 권장안

### 5.1 데이터 규모 재집계

| 구분 | 건수 | 비고 |
|---|---|---|
| A~F그룹 실측 실험데이터 (row 1-46) | 46건 | 기존 42건 + 위탁개발보고서 재판독 4건(row43-46) |
| 그중 공정파라미터+물성치 완전 매칭 | 10건 미만 | 부스바 온도상승(row20-28, 9건)이 최다 |
| 신규 확보 논문 벤치마크 (본 작업, external_benchmark_papers_summary) | 15건 (기존7건+신규8건) | 논문별 공정조건+수치 요약, 개별 row 형태는 아님 |
| **총 (공정조건, 물성치) 페어 추정** | **약 55~60건** | 46건(실측) + 논문벤치마크 중 공정조건-물성치가 함께 명시된 약 9~14건(신규 8건 중 Huang/Zhang/Kondrashov/Kashani/Pan 등 5건은 조건-수치 매칭 완전, 나머지는 부분적) |

**결론**: 총 데이터 규모는 여전히 60건 미만으로, 딥러닝에는 명백히 부족하고 고전 ML(회귀/트리 기반) 또는 데이터 효율적 방법론이 필요한 규모임 — 기존 5절(ML 모델 학습 가능성 평가)의 결론과 동일한 방향이나, 논문 데이터 편입으로 **입력 공간(온도 범위, 저온CVD 등)이 확장**되어 외삽 위험은 다소 완화됨.

### 5.2 최종 권장 ML 방법론

**권장안: 가우시안 프로세스 회귀(Gaussian Process Regression, GPR) 우선 적용 + 랜덤포레스트(Random Forest) 보조 검증, 선형/다항회귀는 단일변수 반응곡선(전류→온도상승 등)에 한정 사용**

| 방법론 | 적용 영역 | 근거 |
|---|---|---|
| **가우시안 프로세스(GPR)** | 전체 공정파라미터→물성치 예측 (주모델) | 데이터가 55~60건 수준으로 극소량일 때 GPR은 (1) 불확실성 정량화(신뢰구간)를 기본 제공하여 "이 예측을 얼마나 믿을 수 있는가"를 명시할 수 있고, (2) 커널 선택으로 물리적 사전지식(예: 온도-저항 관계의 매끄러움)을 반영 가능하며, (3) 소량 데이터에서 트리기반보다 과적합에 안정적임. GAIQ처럼 "실측이 부족하지만 물리모델적 사전지식(ρ∝La⁻¹ 등)이 존재"하는 상황에 이상적 |
| **랜덤포레스트/그래디언트부스팅** | 부스바 온도상승(9건), 저항변화 등 상대적으로 데이터가 밀집된 하위영역의 보조/검증모델 | 비선형 상호작용을 포착하되 GPR과 교차검증하여 방법론 편향을 상쇄 |
| **단순 회귀(선형/다항)** | 단일변수 반응곡선(전류→온도상승, row20-28처럼 12개 조건의 체계적 매트릭스) | 물리적으로 명확한 단일 입력-출력 관계에 한해 해석가능성이 높고 신뢰도 높음 |
| **딥러닝(신경망)** | 비권장 (여전히) | 60건 미만 데이터로는 과적합 필연적. 최소 수백~수천 건 확보 후 재검토 |

### 5.3 실행 로드맵

1. **1단계(현재~단기)**: GPR을 주모델로 구축, 46건 실측 + 신규 논문벤치마크(조건-수치 매칭되는 약 9건)를 학습데이터로 결합. RBF/Matérn 커널로 온도·가스유량 등 연속변수 반응을 모델링.
2. **2단계(중기)**: 위탁개발보고서 원본 이미지 재판독, IR카메라 원본 데이터 확보 등으로 실측 데이터를 100건 이상으로 확충 → 랜덤포레스트/그래디언트부스팅으로 전환 검토.
3. **3단계(장기)**: 실측 500건 이상 확보시에만 신경망(또는 물리기반 신경망 PINN) 검토. 그 전까지는 GPR+RF 앙상블을 "경험적 lookup table + 불확실성 정량화" 도구로 운영.

### 8.2 발견 및 수정한 버그: ML GPR 모델이 API로 절대 트리거되지 않던 구조적 결함

**증상**: `POST /batches/{id}/ml-predictions {"targetMetricCode":"SURFACE_TEMP_C"}` 호출 시 항상 `RULE_BASED_FALLBACK`으로만 응답하고, 실제 학습된 GPR 모델(R²=0.99)의 예측값이 절대 나오지 않음.

**원인**: `ml/models/registry.json`의 SURFACE_TEMP_C GPR 모델은 `features=["current_A","busbar_sq"]`로 학습되었으나, 이 두 값을 API로 입력하는 유일한 경로인 `POST /batches/{id}/process-params`의 `paramName` 컬럼에는 DB CHECK 제약(`synthesis_process_param_param_name_check`, V1 마이그레이션)상 CVD 공정변수(CHAMBER_TEMP_C 등)만 허용되어 있었음 — `current_A`/`busbar_sq`를 저장할 방법이 전혀 없었음. 그 결과 `MlPredictionService.predict()`가 FastAPI에 보내는 `inputParams`에 해당 피처가 항상 빠져 있어 `MissingFeatures` 응답 → 폴백으로 귀결.

**수정**: `V4__add_ml_feature_params.sql` 마이그레이션 추가 — CHECK 제약에 `current_A`, `busbar_sq`(ML서비스 피처명과 대소문자까지 정확히 일치) 추가, `docs/api-contract/01-gaiq-core.yaml`의 해당 enum도 동기화.

**재검증**: `current_A=200, busbar_sq=80`으로 process-param 등록 후 ML예측 재호출 → `predictedValue=12.2658, predictedStdDev=0.4749, confidenceLevel=MEDIUM` (ML서비스(8115)에 동일 입력으로 직접 호출한 결과와 정확히 일치) 확인. 백엔드/ML 로그에서 폴백 경고가 더 이상 발생하지 않음을 확인.

**교훈**: curl 레벨 검증에서 "200/201 응답"만 확인하고 응답 바디의 `confidenceLevel`/`algorithm`까지 대조하지 않았다면 이 결함을 놓칠 수 있었음 — 향후 통합검증 시 응답 코드뿐 아니라 실제 값의 의미(폴백 여부)까지 확인하는 것이 중요.
